# 進め方

## 大原則（どのフェーズでも変わらない）

ここに書いてあるのは、タスクの目的が何であっても守るものだけです。
「何をするか」「何をしてはいけないか」は、現在のフェーズの `00_目的と規則.md` にあります（`02_フェーズとは.md`）。
目的によって、成果物も禁止事項も変わります。
前のフェーズの規則を、今のフェーズに持ち込まないでください。

### 1. そのフェーズの `00_目的と規則.md` に沿う

- そこに書かれていないことを、気を利かせてやらない。
- そこに書かれていることを、勝手に削らない。
- 範囲外に気づいたことは、やらずに `out/00_進捗.md` の「次のフェーズに送るもの」へ書く。

### 2. 事実と推測を必ず分ける

- 事実 = API のレスポンスに実際に含まれていたもの
- 推測 = そこから導いた解釈

書き分けの例:

ECS クラスタ `app-prod` にサービスが 2 つある（事実）。
名前から API と Web に対応すると思われるが、コンテナイメージを確認していないため未確認。

推測を事実のように書かないでください。 後から読む人が検証できなくなります。

### 3. 読めなかったものも記録する

権限で拒否されたものは「拒否された」と書いてください。空白と「確認できなかった」は別物です。
セッションポリシーで意図的に塞いでいるものもあるため、拒否自体は異常ではありません。

### 4. 使ったコマンドを残す

その回の調査ログの末尾に、実際に叩いたコマンドを列挙してください。再現できることが重要です。
統合版には書きません。あちらは構成を語る文書で、作業の記録ではありません。

### 5. 断定を避ける場面

複数の世代が並行稼働していることがあります（`out/01_システム概要.md` を確認し、
書かれていなければユーザーに聞いてください）。
そのとき、「重複している」「使われていない」と見えるものが現役の可能性があります。
断定せず、判断材料（最終更新日時、メトリクス、アクセスログの有無）を添えてください。

これは評価してはいけないという意味ではありません（評価してよいかは `00_目的と規則.md` で決まります）。
評価するにせよしないにせよ、根拠を添えるということです。

## セッションの型

この作業環境は頻繁に作り直され、資格情報にも有効期限があります。
`out/` だけが唯一の記憶です。次の型を守ってください。

### 開始時

`out/` に台帳や `00_目的と規則.md` がまだ無いなら、それを作るところからです（`method/00_開始と再開.md` の
「`out/` に何も無いなら、そこから作ります」）。**とくに `out/_環境/00_動作確認.md` が無ければ、
`03_環境の確認.md` を先にやってください。**

1. `survey-status` を実行する（残り時間と、いま何をすべきかが表示されます）
2. `out/00_進捗.md`（全体の台帳）で、いまどのフェーズかを確認する
3. そのフェーズの `out/<フェーズ>/00_目的と規則.md` を読む
   → 目的・成果物・このフェーズの規則・完了条件。今回の「やる / やらない」はここが正
4. `out/<フェーズ>/02_進捗.md`（フェーズの台帳）で、現在地と次にやることを確認する
5. `out/01_システム概要.md` で、対象について分かっていることを確認する
6. `aws sts get-caller-identity` で身元を確認する
7. 「次にやること」に書かれた作業から着手する

その回の調査ログは、現在のフェーズの `log/` に置きます（下記「成果物の置き場所」）。
フェーズの範囲外に気づいたことは、着手せず全体の台帳の「次のフェーズに送るもの」へ書いてください。

その回にどこまでやるかは、`survey-status` の表示に従って決めてください。

| 表示 | 判断 |
| --- | --- |
| 新しい領域に着手して構いません | 新しい領域に入ってよい |
| 着手中の領域を仕上げてください | いま触っている範囲を閉じる。新しい領域には入らない |
| 新しい作業に着手しないでください | 着手しない。 保存と台帳の更新に充てる |

1 回のセッションに与えられる時間は、回によって違います。
判断の境目は `survey-status` がその都度計算して表示します。
「残り何分なら何をしてよい」を自分で決め打ちにしないでください。
表示は作業中いつでも取り直せます。長い作業に入る前に見直してください。

### 終了時（必ずやること）

1. その回の調査ログを現在のフェーズの `log/` に保存する
2. **分かったことを `report/構成報告.md` の本文に反映する。** 統合版がまだ無いなら、この回はログだけで構いません。
   既にあるなら、**該当箇所を直接書き直してください**（末尾に追記しない・「追加調査で判明」と注記しない。
   下記「統合版に履歴を書かない」）
3. 人が調べないと答えが出ないことを `report/ユーザー確認事項.md` に移す（下記）
4. 台帳を更新する。台帳は 2 つあり、書く内容が違います（下記「台帳の使い分け」）
5. その回に「次からはこう調べればいい」と分かったことを `out/02_調査ノウハウ.md` に書く（下記）

統合版に一通り書き終えた回は、そこで終わりにしてください。
**自分が書いた統合版を同じ回で検証しない**（`method/05_報告の検証.md`）。
台帳の「次にやること」に検証を書いて渡します。

### `ExpiredToken` が出たら

作業を止め、その時点までの結果を `out/` に保存し、進捗を更新してから、
ユーザーに再発行を依頼してください。書きかけのまま失わないことを優先します。

## 成果物の置き場所

`out/` はフェーズごとのフォルダに分かれています。平置きにしないでください。

```
out/
├── 00_進捗.md ← 全体の台帳。現在のフェーズはここが正
├── 01_システム概要.md ← 対象について分かったこと。あなたが書き、育てる
├── 02_調査ノウハウ.md ← 効いた調べ方・読み違いの類型。フェーズをまたいで積む
├── _環境/ ← この環境自体の記録。フェーズの成果物を入れない
└── 01_基礎調査/ ← 現在のフェーズ（例）
    ├── 00_目的と規則.md ← このフェーズの目的と規則（承認後は書き換えないこと）
    ├── 01_調査項目.md ← 何を調べるかの一覧
    ├── 02_進捗.md ← そのフェーズの台帳
    ├── report/ ← 人に渡すもの。このフェーズの成果物（下記）
    │   ├── 構成報告.md ← 統合版
    │   └── ユーザー確認事項.md ← 人が調べないと答えが出ないこと
    ├── log/ ← 各回の調査ログ。成果物ではない（下記）
    └── raw/ ← API の生データ（`raw-` で始める）
```

フォルダが 3 つ並んでいるのは、**`raw/` → `log/` → `report/` という流れ**をそのまま表しています。
直下に残る `00_` 〜 `02_` は、そのフェーズの定義と台帳です。

### 一次記録が 2 つ、成果物が 1 束

`raw/` と `log/` は読み物ではありません。**人が読むのは `report/` だけ**です。

| | 何か | 何が書いてあるか | いつ読むか |
| --- | --- | --- | --- |
| `raw/` | API の生データ | 機械が吐いたそのまま | 問いが起きたとき `jq` で引く |
| `log/` | その回の調査ログ | 何を見て、何が分かり、何が分からなかったか | 統合版を書くときだけ |
| `report/` | そのフェーズの成果物 | いま何がどうなっているか | いつも |

`report/` に何を置くかは、そのフェーズの `00_目的と規則.md`「成果物」が決めます。
基礎調査なら `構成報告.md`（調査項目の順にまとめた統合版）と `ユーザー確認事項.md` の 2 つです。
ファイル名に番号は付けません。**種類はフォルダが表すので、番号で表す必要がありません。**

`log/` は使い捨てです。統合版に取り込んだら、以後は基本的に読み返しません。
同じ問いが起きたら `log/` を遡るのではなく **`raw/` を引き直してください**。
`log/` を読み直すのは `raw/` を読み直すのと結局同じことで、
しかも解釈が一枚挟まっている分だけ不正確です。

`log/` の中は `01_` から、調べた順に増やします。
1 回のセッション、または 1 領域につき 1 ファイルです。

### 統合版に履歴を書かない

`report/構成報告.md` は**現在形**で書きます。いま何がどうなっているか だけを書いてください。

| ✗ 書かない | ✓ こう書く |
| --- | --- |
| 「第 3 回では〜としたが、第 4 回で訂正した」 | 訂正後の記述だけを書く。旧記述は残さない |
| 「前回の読み違いを補正」「追加調査で判明」 | 判明した内容だけを書く |
| 「2026-09-01 ユーザー確認済み」「オーナー決定」 | 決まった内容だけを書く |
| 経緯・試行錯誤・誰がいつ何と言ったか | 書かない。それは `log/` の仕事 |

**間違いが見つかったら、本文を直接書き直してください。** 注記を足して両論併記にしないこと。
何が正しいかが読み手に分からなくなり、読む時間もトークンも二重にかかります。
**訂正の履歴を残したいなら `log/` に残ります。** 統合版は履歴の置き場所ではありません。

根拠は **`raw/` のファイル名だけ**添えます（例: 「…CloudFront は 12 件（`raw-cf.json`）」）。
`log/` の節番号を出典にしないでください。読み手をログへ連れ戻すことになります。

**`raw/` に無いもの（口頭で聞いた背景、複数の API を突き合わせて初めて言えること）は、
出典を書かずに言い切ってください。** 報告書は言い切るものです。裏を取りたい人は `raw/` を引きます。

⚠️ ただし **「事実と推測を分ける」は統合版でも守ります**（大原則 2）。
出典を落とすことと、推測を事実のように書くことは別です。

### 番号とフォルダの意味

**種類はフォルダが表します。番号が付くのは、直下の定義と台帳だけです。**

| | 何を置くか |
| --- | --- |
| `00_` `01_` `02_` | フェーズの定義と台帳（目的と規則・調査項目・進捗）。**読む順**であって、時系列ではない。`out/` 直下も同じ帯（台帳・システム概要・調査ノウハウ） |
| `report/` | そのフェーズの成果物。人が読むのはここ |
| `log/` `raw/` | 一次記録。読み物ではない |

**同じ番号を 2 つのファイルに使わないでください。**
時系列で増えるのは `log/` の中だけです。フェーズのフォルダ直下は、
回を重ねてもファイルが増えません。

| 置くもの | 置き場所 |
| --- | --- |
| その回の調査ログ（Markdown） | 現在のフェーズの `log/`。`01_` から調べた順に。Write ツールで保存する |
| `aws` の生の出力 | 現在のフェーズの `raw/`（例: `> out/<フェーズ>/raw/raw-sg.json`） |
| 分かったことの結論 | 現在のフェーズの `report/構成報告.md`（本文を書き直す。下記） |
| 人が調べること | 現在のフェーズの `report/ユーザー確認事項.md`（下記） |
| 次も効く調べ方・読み違いの類型 | `out/02_調査ノウハウ.md`（下記） |

### 台帳の使い分け

台帳は 2 つあります。混ぜると、フェーズが増えるたびに読めなくなります。

| | `out/00_進捗.md`（全体） | `out/<フェーズ>/02_進捗.md`（フェーズ） |
| --- | --- | --- |
| 粒度 | フェーズの単位。薄く保つ | セッションの単位。厚くてよい |
| 書くこと | 現在のフェーズ / フェーズの一覧と状態 / 次のフェーズに送るもの | 現在地 / 完了したこと / 次にやること / 未解決の疑問 / 読めなかったもの / 生データの索引 |
| 判断基準 | フェーズが変わっても価値が残るか | そのフェーズの中でだけ意味があるか |

全体の台帳に書くものは、次の 3 つに限ります。

1. どのフェーズにいるかと、各フェーズの状態
2. ユーザーから聞いた背景（AWS の API では読めない事実。どのフェーズでも前提にしてよい）
3. 決定事項（このアカウントを扱ううえで決めたこと）

その回に何をしたか、何が残っているかは、フェーズの台帳に書いてください。
全体の台帳に積み上げないこと。

### `out/02_調査ノウハウ.md` に、次も効くことを書く

調べていると「**次からはこう調べればいい**」と分かる瞬間があります。
それを会話の中に置いたままにすると、セッションが終わった時点で消えます。

| 書くもの | 例 |
| --- | --- |
| 効いた調べ方 | どの API を叩くと、何が一度に分かるか |
| 読み違いの類型 | 何を信じると間違えるか（名前・作成日時・一覧の欠落など） |
| 遠回りだったこと | 次はやらなくてよいこと |

例はこのアカウントのもので構いませんが、**教訓は別のアカウントでも通じる形で書いてください。**
台帳（現在地）とも、システム概要（対象そのものの前提）とも別のファイルです。混ぜないこと。

**ここに書いてあることと違う挙動を見つけたら、「違った」と書いてください。**
この文書（`method/`）は書き換えられませんが、`out/02_調査ノウハウ.md` には書けます。

### ユーザーに聞くのは、あなたの仕事です

対象システムについて、あらかじめ用意された資料はありません。
リポジトリも設計書も見えず、`out/` にあるのは、これまでのセッションが自分で書いたものだけです。

だから、聞かないと分からないことは、その場でユーザーに聞いてください。
この作業環境ではユーザーと対話できます。推測で埋めないでください。

聞くことの例

- 「このシステムは何をするものですか」「利用者は誰ですか」
- 「このリソースは意図してこうなっていますか」「これはもう使っていませんか」
- 「`◯◯` という名前は何を指しますか」「この環境は誰が使っていますか」
- 「`prod` / `stg` / `dev` はそれぞれどれですか。AWS 上に無いものはありますか」

| 状況 | どうする |
| --- | --- |
| その答えが無いと、次の調査手順が決まらない | すぐ聞く。推測で進めない |
| その答えで、いま書いている記述が変わる | すぐ聞く |
| 後でまとめて答えてもらえばよい | `report/ユーザー確認事項.md` に積む（下記） |
| ユーザーが席にいない・返事が来ない | `report/ユーザー確認事項.md` に積んで、調査は先へ進める |

聞いた答えは、必ず `out/01_システム概要.md` に書いてください。
会話の中だけに残すと、セッションが終わった時点で消えます。
この環境は使い捨てで、`out/` だけが記憶です。

### `out/01_システム概要.md` を育てる

これは「対象システムについて分かったこと」を積み上げていくファイルです。
初回は空か、ごく短いところから始まります。セッションごとに書き足してください。

| 書くこと | 例 |
| --- | --- |
| 何のシステムか・利用者は誰か | ユーザーに聞く |
| アプリケーションの構成要素 | ユーザーに聞く |
| 世代と系統（旧環境・現行・進行中のものが並行していないか） | ユーザーに聞く。これを外すと読み違えます |
| 名前と実態が一致しないもの | ユーザーに聞く。名前から用途を推測しないため |
| `prod` / `stg` / `dev` の実体（AWS 上に無い環境があるか） | ユーザーに聞く |
| 固有名詞・略語の意味 | ユーザーに聞く |

AWS の構成そのものは、ここに書かないでください。 それは調査結果であって、統合版に書きます。
ここに書くのは、AWS を見ても分からない、対象そのものの前提です。

出どころを必ず書いてください（「ユーザーに確認済み」／「未確認・推測」）。
後から読む人が、どこまで裏が取れているかを判断できる必要があります。

前のセッションが書いたことでも、実態と食い違って見えたら鵜呑みにしないでください。
ユーザーに聞いて、直してください（このファイルは書き換えてよい唯一の前提資料です）。

### その場で答えが出ないものは、調査結果に混ぜない

聞けなかった問い・すぐには答えが出ない問いは、
`report/ユーザー確認事項.md` に分けて集めてください。

このファイルは、それ単体を読むだけで確認事項の意図が分かるように書きます。
調査結果を開かないと意味が通らない書き方をしないこと。出典として節番号を添えるのは構いませんが、
添えた参照を読まなくても確認できる状態にしてください。1 項目につき次の 5 つを書きます。

1. 確認したいこと（1 文の質問。短い事実で答えられる形に）
2. なぜ聞くのか（この答えで何が決まるのか）
3. こちらで分かっている事実（ここだけ読めば話が通じる粒度で）
4. なぜ AWS 側から分からないのか（権限 / 原理的に不可 / 外部のもの）
5. 答えの使い道

書き方は現在のフェーズの `00_目的と規則.md` に従うこと（基礎調査では、指摘リストやリスク一覧の体裁で書きません）。
これは「構成を読み解くために事実が足りない箇所」の一覧です。

## コマンドの作法

| 決まり | 理由 |
| --- | --- |
| `aws` は単独で実行する | パイプ・`&&`・`bash -c` はこの環境では実行できません（`> out/…/名前.json` の保存だけは通ります） |
| EC2 の中は `ec2 <host> <動詞>` で | 登録済みのホストに限る。`aws` と同じ作法（単独で実行、保存は `> out/…/名前.txt`）。動詞と進め方は `06_EC2の中を調べる.md` |
| Lambda のコードは `code/` を読む | 取り出してある関数に限る。コードの URL はこの環境では取得できない。読み方は `07_Lambdaのコードを読む.md` |
| 絞り込みは `--query` と `--output` | 上記の制約下での標準手段 |
| `--max-items` を必ず付ける | API レート制限と、本番の CloudTrail 汚染を防ぐため |
| 生データは `> out/<フェーズ>/raw/raw-名前.json` で保存する | 出力が文脈を経由するとトークンを浪費するため |
| レポート（Markdown）の保存は Write ツール | |
| リージョンは指定しなくてよい | 既定のリージョンが設定済みです。他リージョンを見る必要が出たら `--region` を明示し、理由を添える |

### この環境で通らない書き方と、その回避

`aws` を含むコマンドは、`;` やパイプ、リダイレクトと組み合わせると実行できません。
`> out/<フェーズ>/raw/名前.json` への保存だけが例外です（相対パスのみ。絶対パスは通りません）。

| やりたいこと | 通らない書き方 | 通る書き方 |
| --- | --- | --- |
| 長いコマンドを読みやすくする | 改行、`\` による行継続 | 1 行で書く。引数が多いときは `--cli-input-json file://out/<フェーズ>/raw/名前.json` でファイルに渡す |
| 文字列 `aws` を含むパターンで絞る | `grep '^/aws/lambda/' … \| head`・`sed -n '/aws/p' …` | `grep` / `rg` / `cat` / `head` / `wc` / `ls` をファイルに対して**単独で**実行するなら、`aws` や `boto3` を書いてよい（`grep -rn boto3 <ディレクトリ>`）。それ以外（`sed` や `jq` のフィルタ）では、`sed -n 's#^/.ws/lambda/##p'`・`test("^/.ws-service-role/")` のように、**ワイルドカードで `aws` の字面を避ける** |
| 同じ API を対象を変えて何度も叩く | `for` ループ | 1 つずつ実行する。**独立したコマンドは 1 回の応答でまとめて投げると速い** |
| 多数の対象を 1 回で問い合わせる | `for` ループ | ⭐ **クエリを JSON に書いてファイルで渡す**（例: `cloudwatch get-metric-data --metric-data-queries file://out/<フェーズ>/raw/queries.json`）。ループが使えない制約の、最も効く回避策 |
| 出力をファイルに落とす | 絶対パス | 相対パスの `> out/<フェーズ>/raw/名前.json`。位置引数で出力先を取る API（`cloudfront get-function` など）にも同じ形で渡せる |

### `--query`（JMESPath）の癖

- バックティックは使えません。`||` と `|`（パイプ演算子）も通りません
- `keys()` は使えます（例: `keys(Environment.Variables)`）。
  **ただし対象が `null` だとエラーになる**ので、`[?Environment.Variables!=null]` で先に絞ってください
- `--filter` に渡す JSON は、エスケープすれば通ります

### ページングの癖

**`--max-items` が効かない API があります。** `--max-results` や `--limit` を使うか、上限が API 側で決まっています。

`apprunner list-services` / `describe-service`（`--max-results`・上限 20）/ `wafv2 list-web-acls`（`--limit`）/
`timestream-write list-databases` / `synthetics describe-canaries` / `workmail list-*` / `chatbot describe-*` /
`codestar-notifications list-notification-rules`（`--max-results`）/ `budgets describe-*`（`--max-results`）/
`imagebuilder list-*`（`--max-results`）

`resourcegroupstaggingapi get-resources` は `--resources-per-page` と `--max-items` を併用できません。

この一覧が網羅である保証はありません。弾かれたら、そのコマンドの `help` で対応するオプションを確かめてください。

## 大きな出力の扱い

`aws` の出力をそのまま受け取ると、リソースが多いときにトークンを浪費し、
限られたセッション時間の中で調査が終わりません。次の 2 段階に分けてください。

```
aws ec2 describe-instances --max-items 100 > out/<フェーズ>/raw/raw-ec2.json
jq '[.Reservations[].Instances[] | {id:.InstanceId, type:.InstanceType, state:.State.Name}]' out/<フェーズ>/raw/raw-ec2.json
```

| 決まり | 内容 |
| --- | --- |
| 保存先 | 現在のフェーズの `raw/` 配下。拡張子は `json` / `txt` / `csv` |
| 命名 | 生データは `raw-` で始める（レポートと区別するため） |
| 読み方 | `cat` で全部読まない。 `jq` で必要な部分だけ取り出す |
| 再利用 | 保存した JSON は何度でも別の観点で問い合わせ直せる。 API を叩き直さないこと |
| 過去のフェーズの `raw/` | 読んでよい。むしろ先に読む。 同じ問いに API を叩き直さない |

最後の 2 点が重要です。API の再実行は、レート制限と本番の CloudTrail 汚染につながります。

## 効率のよい入口

全リージョン・全サービスを総当たりしないでください。次の 2 つで当たりを付けてから深掘りします。

```
aws ce get-cost-and-usage --time-period Start=<先月の1日>,End=<今月の1日> --granularity MONTHLY --metrics UnblendedCost --group-by Type=DIMENSION,Key=SERVICE --region us-east-1
```
→ 課金が発生しているサービス＝実際に動いているものが 1 回で分かります。
   Cost Explorer は `us-east-1` のみです。`Key=REGION` に変えればリージョンの当たりも付きます。

```
aws resourcegroupstaggingapi get-resources --resources-per-page 100 > out/<フェーズ>/raw/raw-tagged.json
```
→ タグ付きリソースの一覧。タグの無いものは出ない点に注意してください。
   件数が多いのでファイルに落としてから `jq` で読んでください。
