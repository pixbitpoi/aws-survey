# 基礎調査のあと — ユーザーと進める

基礎調査の報告（`out/01_基礎調査/report/構成報告.md`）は、AWS の API で見える外側から書いたものです。
「何があり、どう繋がっているか」は分かっても、「何をどうやって提供しているか」には穴が残ります。
ここからはユーザーと対話しながら、その穴を埋めます。

## 3 つの穴と、それぞれの埋め方

| 穴 | 誰が埋められるか | どうする |
| --- | --- | --- |
| EC2 の中（何が動いているか・ログ・設定） | この環境（経路があれば） | `survey-status` に出ているホストなら、聞かずに `ec2 <host> …` で読む（`method/06`）。無ければ依頼文を伝える |
| Lambda の中（コードが何を呼び、どこへ繋ぐか） | この環境（取り出してあれば） | `code/` にあれば、聞かずに読む（`method/07`）。無ければ依頼文を伝える |
| AWS の外（GitHub Actions・Cloudflare・他の SaaS・DNS の登録先・利用者・運用の事情） | ユーザーだけ | 聞く。AWS からは原理的に分からないので、推測で埋めない |

線引きはこれだけです。**アカウントの中で調べられることは、ユーザーに聞く前に調べる。** 外のことは聞く。
「Lambda が参照する DB がこのアカウントに無い」は、全リージョンと Secrets の名前まで確かめてから聞く問いであって、
最初の一覧で見当たらなかった時点で聞く問いではありません。

## 頼まれたことは、その場でやる

対話の回では、ユーザーの質問と依頼が最優先です。台帳の予定や、前の回が書いた「次にやること」より優先します。

- 質問には、その場で答える。答えに調査が要るなら、調べてから答える（`raw/` にあれば引く。無ければ API を叩く）
- 依頼は、その場でやる。事前の計画書や承認は要りません。やることが大きければ、進め方を一言添えて始める
- 報告に載っていないことを聞かれたら、調べて答え、報告の本文にも足す（`method/01`「統合版に履歴を書かない」）
- 答えられないことは、何が分かれば答えられるかを添えて「分からない」と言う

「予定に無い」「先に決めてから」で断らないでください。予定はユーザーのためにあり、ユーザーの求めを断る根拠にはなりません。

## 報告を育てる

対話で分かったことは、その場で `report/構成報告.md` の本文に反映します。別の報告書を新しく作らず、同じファイルの該当箇所を書き直します。
ユーザーから聞いた前提は `out/01_システム概要.md`、その回の経緯は `log/`、次も効く調べ方は `out/02_調査ノウハウ.md` です。
`report/ユーザー確認事項.md` は、答えが出た項目を消して、新しく出た問いを足します。答えた内容は報告と概要に移っているので、履歴は要りません。

基礎調査は、AWS の中で分かることを言い切るまで続きます。中を読んで役割が分かった EC2 や Lambda は、報告の C（コンピュート）にそのまま書きます。
基礎調査の中で書くもの・書かないもの（評価や提案を書かない）は `method/04` にあります。

## 別の種類の仕事を頼まれたら

「セキュリティを監査して」「コストを下げる案を」「この変更の影響範囲を」「構成図を」のように、
基礎調査とは性質の違う仕事を頼まれたら、`out/` に新しいフォルダを作って、そこで進めます。

1. `out/NN_<仕事の名前>/`（`02_` から。`raw/` `log/` `report/`）と、その `02_進捗.md`（何を頼まれたか・現在地）
2. `out/00_進捗.md` の「作業の一覧」に 1 行足し、「現在の作業」を書き換える
3. 基礎調査の `report/` と `raw/` を土台にする。同じ問いを AWS に叩き直さない

その仕事で何を書いてよいかは、仕事の性質で決まります。**監査なら評価することが成果物**で、基礎調査の「評価や提案を書かない」は当てはまりません。
逆に、監査の途中で構成の事実が新しく分かったら、それは基礎調査の報告の本文に足します（事実の置き場は 1 つ）。

過去の仕事の `report/` は書き換えません。訂正が要るなら、いまの仕事の報告に書き、古いほうには「→ `NN_…` で訂正」と 1 行足します。
例外は基礎調査の `report/構成報告.md` で、これは現状の事実を集める場所なので、いつでも最新に書き直します。
