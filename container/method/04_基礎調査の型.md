# 基礎調査の型

最初の仕事は基礎調査です。このアカウントに何があり、どう繋がっていて、何を提供しているらしいかを、
AWS の API で見える範囲で明らかにし、報告に書きます。以後のあらゆる作業（中を読む・監査・計画・資料作成）の土台です。

どの AWS アカウントでも同じ型で進めます。ユーザーに目的や対象の説明を聞いてから始めるものではなく、
白紙で調べて報告を書き、それを手にユーザーと話します（`method/02_基礎調査のあと.md`）。

## 基礎調査で書くもの・書かないもの

これは構成の把握であって、監査ではありません。

- 広い許可、公開設定、ログの保持期間、課金額は、構成を理解するための材料として記録する。
  リスク評価や削減提案は、基礎調査の成果物ではない
- 「不要」「消してよい」と判断しない。気づいたことは事実として記録するに留める
- 「これは危ない」「これは無駄だ」と書きたくなったら、代わりに「何がどこに繋がっていて、いつから動いているか」を書く

ただし「なぜそうなっているか」まで踏み込むのは範囲内です。未確認・不明として残ったものを追加の問い合わせで潰すこと、
リクエストやデータがどこをどう通るかを集めた事実から辿ることは、基礎調査の仕事です。

土台を作る段階で評価を混ぜると、事実と判断が分離できなくなります。監査を頼まれたら、そのときは評価が成果物になります
（`method/02`「別の種類の仕事を頼まれたら」）。

---

## 工程 1: 生データを集める（`raw/`）

対象についての資料は何もありません。先入観を持たずに「何があるか」を列挙します。知ってから見に行くと、想定外のものを見落とします。

入口は `method/01_進め方.md` の「効率のよい入口」です。Cost Explorer が読めれば、課金のあるサービスとリージョンから当たりを付け、
そこから `describe-*` / `list-*` で実体を並べます。読めなければ、有効化の依頼は `report/ユーザー確認事項.md` に書き、
`resourcegroupstaggingapi` とリージョンごとの `describe-*` で進めます。

集めるのは、下の「調査項目」の A〜I が答えられるだけの生データです。**全部を集めてから書くのではなく、領域ごとに集めて書いても構いません。**
どちらでも、生データは必ず `.survey/raw/`（`> out/.survey/raw/raw-名前.json`）に残します。
これは次の回と、次の仕事のための資産です。同じ問いに API を叩き直さずに済むように、名前で中身が分かるようにしてください。

一覧が空だったサービスも、空だった生データを残します。「無かった」と「見ていない」を区別するためです。

主に見るリージョン以外にも、課金や Resource Explorer で当たりが付いたリージョンは見ます。当たりが付かなかったリージョンは、
見ていないことを報告に書きます。

## 工程 2: 報告を書く（`report/`）

生データが揃ったら、`report/構成報告.md` と `report/ユーザー確認事項.md` を書きます。この 2 つが基礎調査の成果物です。
人が読むのはこれだけで、`raw/` と `log/` は読み物ではありません（`method/01`「成果物の置き場所」）。

ユーザーが応答できない回でも、この工程まで終えてください。生データだけ残して報告が無い状態は、ユーザーには何も伝わりません。

### `report/構成報告.md`

報告が答える問いは「このアカウントは何を、どう提供しているか」です。**リソースの一覧ではありません。**
「IAM ロールは 9 個」のようにカテゴリごとに数えた文は、読み手に何も伝えません。読み手が知りたいのは、
どの入口から入ったリクエストがどこを通ってどのデータに届くか、そのために何がどう繋がっているかです。
数と一覧は付録に降ろし、本文は繋がりだけを書きます。次の 5 つの節を、この順に置きます。

**1. 概要。** 集めた事実から言える「このアカウントは何を提供しているらしいか」を数段落で。系統がいくつあるか、
それぞれの入口と主な構成要素、動いている根拠（メトリクス・課金）まで。名前や環境変数から用途を推した箇所は、
推測と分かるように書きます（`method/01` 大原則 2）。事実と推測を分ければ、推測を書くことは構いません。
推測を書かないと、報告が一覧の寄せ集めになります。

**2. システムごとの経路。** 見つけた系統を 1 つずつ小見出しにし、入口（ドメイン・CloudFront・ALB・API Gateway・関数 URL・
イベント）→ コンピュート（何が、どのランタイム・イメージで）→ データストア（何を読み書きするか）の順に、辿れたところまで辿ります。
ネットワーク・権限・監視・稼働状況はカテゴリとして別に立てず、**その系統に付随する事実として、その系統の中に書きます。**
「この Lambda の実行ロールには参照先の S3 への許可が無い」「このインスタンスの SG に受信規則が無い」「直近 30 日の呼び出しは 0」は、
それぞれ H・B・I の節に散らすのではなく、その系統の話として 1 か所に集めます。散らすと、繋げれば言えることが言えなくなります。
**複数の事実を突き合わせて初めて言えることを、ここで言ってください。** 設定が名指しするデータストアが存在せず、実行ロールにも許可が無く、
呼び出しの記録も無いなら、「この関数は設定上の参照先に到達できる状態になく、動いた形跡も無い」と 1 文で書きます
（評価ではなく、事実の突き合わせです。「不要」「消してよい」とは書きません）。

**3. どこにも繋がらないもの。** どの系統にも入らなかったリソース、参照先の無い設定、参照されていないリソース。
「見つかったが、繋がりが分からない」ものの置き場です。見当たらないと書く前に、他のリージョン・他の名前・関連する API で確かめます。

**4. 外からは分からないこと。** AWS の API で見える外側からは決められなかったことを、何を見れば決まるかと一緒に書きます。
この節の中身が、次の `ユーザー確認事項.md` になります。

**5. 付録: リソース一覧。** 下の「調査項目」の A〜I を、この順に**表**で置きます。何があって何が無かったかの網羅性はここで担保します。
「無かった」ものも、生データの名前を添えてここに書きます（「無かった」と「見ていない」を区別するため）。
本文に書いた事実を、ここに書き直す必要はありません。数を書くのはここだけです。

| 領域 | 項目 | 結果 | 根拠 |
| --- | --- | --- | --- |
| A | リージョン | 主リージョンのみ（他の 2 リージョンは既定リソースだけ） | `raw-resource-search-*.json` |
| C | EC2 | 3 台 | `raw-ec2-instances.json` |
| D | RDS / Aurora | なし | `raw-rds-instances.json` |

各節は、いま何がどうなっているかを現在形で書きます。経緯・訂正の履歴・「第 N 回」への言及・調査ログへの参照は書きません。
根拠は `raw/` のファイル名だけ添えます（例: 「CloudFront は 12 件（`raw-cf.json`）」）。
読めなかったもの（権限で拒否されたもの）は「読めなかった」と書きます。空白と「確認できなかった」は別物です。

### `report/ユーザー確認事項.md`

ユーザーがこれだけを読んで、何に答えればよいかが分かり、**その場で答えを書き込める**ファイルです。
問いは答えやすい順に並べ、2 つの節に分けます。

**中を見れば分かること。** AWS の API では外側しか見えず、中を読めば決まるもの。EC2 の中（何が動いているか・設定・ログ）と
Lambda のコード（何を呼び、どこへ繋ぐか）が典型です。ECS のタスク定義やコンテナイメージも同じ扱いです。
`survey-status` に経路（登録済みホスト・取り出してあるコード）が出ているものは、**ここに書かずに読んで、報告に書きます**
（ユーザーが応答できない回も同じ。`method/00`）。ここに書くのは、経路がまだ無いものだけです。
1 つずつ、**どのリソースを、なぜ見たいか**（その答えで報告のどこが埋まるか）を書き、
用意してもらう依頼文（`method/06` / `method/07` にあるもの）をそのまま添えます。経路が無いものが無ければ、この節は「なし」と 1 行で書きます。

**ユーザーにしか分からないこと。** AWS の外にあるもの（GitHub Actions・Cloudflare・他の SaaS・DNS の登録先）、
利用者・運用の事情・名前の意味・「これは意図してこうなっているか」のように、AWS を見ても決まらないこと。
1 つの問いは次の 3 つで書きます。

```
### Q1. `api-*` の Lambda と EC2 `app1` は、1 つのシステムですか。誰が使うものですか

背景: 主に見るリージョンに `app1` 1 台と `api-orders`・`api-images` があり、どれも同じ用途を示すタグが付いています。
両者を繋ぐ設定は AWS 上に無く、1 つのシステムとして扱うか、別々の環境として扱うかで、報告の系統の分け方が変わります。

回答:
（ここに書いてください）
```

- **見出し**は質問 1 文。`Q1.` から通し番号を振り、短い事実で答えられる形にする（「〜ですか」）
- **背景**は 2〜3 文。こちらで分かっている事実と、答えで何が決まるかを、それだけ読めば話が通じる粒度で。
  「なぜ聞くのか」「なぜ AWS から分からないのか」「答えの使い道」を項目として並べない。それは問いを吟味するときの観点であって、読み手に見せるものではない
- **回答**の欄を空けておく。ユーザーはここに書いて返す。次の回はまずこの欄を読み、書かれていれば `report/前提.md` に移して統合版を書き直し、その問いを消す

**アカウントの中で調べれば決まることを、ここに書かないでください。** 「見当たらない」は、他のリージョン・他の名前・関連する API を
確かめてから書く言葉です。指摘リストやリスク一覧の体裁にはしません。これは「構成を読み解くために事実が足りない箇所」の一覧です。

## 工程 3: ユーザーと埋める

報告を手に、ユーザーと対話しながら穴を埋めます。中を読める経路があれば聞かずに読み、外のことは聞き、
分かったことは報告の本文に書き直します。進め方は `method/02_基礎調査のあと.md` です。

## 調査項目

上から順に 1 つずつ進めてください。対象によっては当てはまらない項目も、足りない項目もあります。
当てはまらない項目は「該当なし」と、生データの名前を添えて書きます。

### A. 全体像

- [ ] このアカウントで実際に動いているリソースの一覧（リージョン別）
      （入口は `method/01` の「効率のよい入口」。Cost Explorer が使えなければ、待たずに続けつつ、有効化の依頼を確認事項に書く）
- [ ] `prod` / `stg` / `dev` がどう分離されているか（タグ・命名規則・VPC・その他）
- [ ] 世代や系統が複数あるなら、それぞれがどこで動いているか、どれが生きているか

### B. ネットワーク

- [ ] VPC・サブネット構成（パブリック / プライベート、AZ 配置）
- [ ] セキュリティグループ。何がどこからの通信を受け付けているか
      （許可元が IP か SG か。SG は世代をまたいで共有されていることがあるので、
      実際に付いているリソースを ENI から引き直すこと）
- [ ] NAT ゲートウェイ、VPC エンドポイントの有無
- [ ] Route 53 のホストゾーンとレコード

### C. コンピュート

- [ ] App Runner / ECS / EC2 / Lambda のうち何が使われているか、それぞれの役割
- [ ] 各サービスがどのコンテナイメージ・ランタイムで動いているか
- [ ] 呼び出し元と呼び出し先（トリガー・環境変数の名前・実行ロールの許可先から辿る）

### D. データストア

- [ ] RDS / Aurora のインスタンスとエンジンバージョン、マルチ AZ か
- [ ] ElastiCache（Redis）の構成
- [ ] DynamoDB のテーブル
- [ ] S3 バケットの一覧と用途。パブリックアクセス設定がどうなっているか（設定の事実として記録する）
- [ ] バックアップの設定と保持期間
      — 何が守られているか＝何が現役とみなされているかの手がかりになる

### E. 配信

- [ ] CloudFront ディストリビューションとオリジン（どれが何を向いているか）
- [ ] ロードバランサー（ALB / NLB）のリスナーとターゲットグループ
- [ ] API Gateway と Lambda の関数 URL
- [ ] ACM の証明書とドメイン、有効期限
      — どのドメインがどのリソースに紐づいているかを逆算する材料

### F. 非同期処理

- [ ] SQS キューの一覧と用途、DLQ の有無と滞留の状況
      （属性で確認する。`receive-message` は本番に影響するため禁止）
- [ ] EventBridge のルールとターゲット
- [ ] Step Functions の有無

### G. 監視とログ

- [ ] CloudWatch アラームの一覧と、通知先（SNS トピックの購読先）
- [ ] ロググループの一覧と保持期間
      — 削除済みリソースの痕跡が残るため、構成の履歴を読む材料になる

### H. 権限と鍵

- [ ] IAM ロールの一覧と、それぞれの信頼関係（誰が使えるか＝何がどこに繋がっているか）
- [ ] IAM ユーザーと、外部の ID プロバイダ（GitHub Actions などの OIDC）
      — AWS の外から何が入ってくるかの手がかり
- [ ] KMS キーの一覧と用途（アプリが署名や暗号化に使っているキーがどれか）
- [ ] Secrets Manager / パラメータストアに何が置かれているか（キー名のみ。値は読めません）
      — キー名から、どのサービスが何に依存しているかが分かる

### I. 稼働状況

- [ ] 課金の内訳から、実際に動いているものを逆算する
      （「存在するか」ではなく「動いているか」を知る、ほぼ唯一の手段）
- [ ] 動いていないように見えるもの（未アタッチの EIP、空の NAT、停止中インスタンスの EBS、
      ロードバランサーに繋がっていないターゲットグループなど）。
      不要と判断せず、そう見える根拠（最終更新日時・紐づけの有無・メトリクス）を添えて記録する

## 完了の目安

- [ ] 付録の表に、調査項目のすべてが、答えか「答えられない理由」のどちらかで埋まっている
- [ ] `report/構成報告.md` が「概要 → システムごとの経路 → どこにも繋がらないもの → 外からは分からないこと → 付録: リソース一覧」の順に揃っている
- [ ] 本文に、カテゴリごとの件数だけを言う文（「〜は N 個」）が無い。数は付録の表にある
- [ ] `report/構成報告.md` に、経緯・訂正の履歴・「第 N 回」への言及・調査ログへの参照が 1 つも無い
- [ ] `report/ユーザー確認事項.md` がそれ単体で読め、各問いに回答欄があり、「中を見れば分かること」には依頼文が添えてある
- [ ] `survey-status` に出ている経路（登録済みホスト・取り出してあるコード）は読んで、報告に書いてある
- [ ] 生データが `raw/` に残り、同じ問いに API を叩き直さずに答えられる
- [ ] 別の回が報告を検証した（`method/05`）
- [ ] ユーザーが `report/構成報告.md` を読み、粒度と不足箇所のフィードバックを返した

## 各回の調査ログ（`.survey/log/`）

- 1 回のセッション、または 1 領域につき 1 ファイル。`NN-<topic>.md` の英語名（例 `01-baseline.md`）で、調べた順に増やす
- 冒頭に調査日時。本文は、何を見て何をそう判断したか・訂正したこと・読めなかったもの
- 叩いたコマンドは監査ログ（`.survey/env/aws-audit.log`）に自動で残るので、列挙しない
