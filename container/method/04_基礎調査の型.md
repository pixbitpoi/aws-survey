# 基礎調査の型

最初のフェーズを「基礎調査」にするときの、目的と規則・進め方・調査項目です。
どの AWS アカウントでも通る型として書いてあります。

これは決まりではなく、たたき台です。ユーザーと相談して取捨選択・追記し、
下記の「目的と規則」を `out/<フェーズ>/00_目的と規則.md`、
「調査項目」を `out/<フェーズ>/01_調査項目.md` として置いてください。
対象によっては当てはまらない項目も、足りない項目もあります。

**先に書くのは目的と規則のほうです。** 何のための仕事かが決まらないうちに項目を並べても、
粒度が決まりません。どちらもユーザーの承認を得てから深掘り（工程 3）に入ります。
工程 1 の白紙の棚卸しは承認前の前段で、目的を聞くための材料です。

---

## 目的と規則のたたき台

`00_目的と規則.md` の草案です。**そのまま置かず、ユーザーに読んでもらってください。**
項目立ては 5 つ（`02_フェーズとは.md`）。以下は基礎調査の場合の中身です。

```markdown
## 目的

このアカウントに何があり、どう繋がっているかを明らかにする。
以後のあらゆる作業（監査・計画・設計・資料作成など）の土台になるフェーズ。

## 成果物

すべてこのフェーズのフォルダに置く。

| 成果物 | 内容 |
| --- | --- |
| `report/構成報告.md` | 調査項目の順にまとめた統合版。**人が読むのはこれだけ。現在形で書き、履歴を持たない** |
| `report/ユーザー確認事項.md` | 人が答えないと埋まらないことの一覧（それ単体で読める形で） |
| `02_進捗.md` | このフェーズの台帳 |
| `log/` | 各回の調査ログ。成果物ではなく、統合版を書くための一次記録 |
| `raw/` | 再利用できる生データ |

## このフェーズの規則

これは構成の把握であって、監査ではない。

- 広い許可、公開設定、ログの保持期間、課金額は、構成を理解するための材料として記録する。
  リスク評価や削減提案は、このフェーズの成果物ではない。
- 「不要」「消してよい」と判断しない。気づいたことは事実として記録するに留める。
- 「これは危ない」「これは無駄だ」と書きたくなったら、代わりに
  「何がどこに繋がっていて、いつから動いているか」を書く。

ただし「なぜそうなっているか」まで踏み込むのは範囲内。

- 未確認・不明として残ったものを、追加の問い合わせで潰すこと
- リクエストやデータがどこをどう通るかを、集めた事実から辿ること

範囲外なのは、集めた事実に対する評価・提案・設計。

## 入力

最初のフェーズなので前段の成果物は無く、あらかじめ用意された資料も無い。
`out/01_システム概要.md` は、ユーザーに聞いて自分で書く（ただし下記の順序で。最初は白紙で棚卸し）。

## 完了条件

- [ ] 調査項目のすべてに、答えか「答えられない理由」のどちらかが書かれている
- [ ] `report/構成報告.md` が調査項目の順に揃っている
- [ ] `report/構成報告.md` に、経緯・訂正の履歴・「第 N 回」への言及・調査ログへの参照が 1 つも無い
- [ ] `report/ユーザー確認事項.md` がそれ単体で読める状態になっている
- [ ] 各回の調査ログの末尾に、実際に叩いたコマンドが列挙されている
- [ ] 生データが `raw/` に残り、同じ問いに API を叩き直さずに答えられる
- [ ] ユーザーが `report/構成報告.md` を読み、粒度と不足箇所のフィードバックを返した
```

「評価や提案を書かない」を規則に入れる理由は、土台を作る段階で評価を混ぜると、
事実と判断が分離できなくなるためです。**普遍の掟ではありません**（`02_フェーズとは.md`）。

---

## 進め方（このフェーズの中の段取り）

これらは「フェーズ」ではなく、フェーズの中の工程です。

1. 白紙で棚卸しする

対象システムについての資料は、まだ何もありません。
先入観を持たずに「何があるか」を列挙してください。
知ってから見に行くと、想定外のリソースを見落とします。

この段階でユーザーに「何のシステムか」を聞かないでください。 次の段で聞きます。

この工程は目的の承認より前にやってよく、ユーザーが応答できない回はここまでで止めます（`method/00`）。
入口は `01_進め方.md` の「効率のよい入口」です。Cost Explorer が読めれば、課金のあるサービスとリージョンから当たりを付け、
そこから `describe-*` / `list-*` で実体を並べます。読めなければ、有効化の依頼は聞ける回に回し、`resourcegroupstaggingapi` と
リージョンごとの `describe-*` で進めます。生データは `raw/` に、見つけたものの一覧と聞きたいことは `log/01_棚卸し.md` に残します。

2. 棚卸しを手に、ユーザーに聞く

見つけたものを手に持って質問するのが要点です。
何があるか分かってからのほうが、問いが具体的になり、答えも具体的になります。

聞いて分かったことを `out/01_システム概要.md` に書きます（`01_進め方.md`「ユーザーに聞くのは、あなたの仕事です」）。

ユーザーの答えと、AWS で見えるものが食い違うことがあります。
食い違いこそが調査の成果です。どちらが誤りとも決めつけず、両方を記録してください。

3. 領域ごとに深掘りし、統合する

調査項目を埋め、`report/構成報告.md` にまとめます。
未確認のまま残ったものは潰し、経路が辿れるところまで辿ります。

---

## 調査項目（たたき台）

全部を一度にやろうとせず、上から順に 1 つずつ進めてください。

### A. 全体像

- [ ] このアカウントで実際に動いているリソースの一覧（リージョン別）
      （入口は `01_進め方.md` の「効率のよい入口」。Cost Explorer が使えなければ、待たずに続けつつ、その場でユーザーに有効化を勧める）
- [ ] `prod` / `stg` / `dev` がどう分離されているか（タグ・命名規則・VPC・その他）
- [ ] 世代や系統が複数あるなら、それぞれがどこで動いているか、どれが生きているか

### B. ネットワーク

- [ ] VPC・サブネット構成（パブリック / プライベート、AZ 配置）
- [ ] セキュリティグループ。何がどこからの通信を受け付けているか
      （許可元が IP か SG か。SG は世代をまたいで共有されていることがあるので、
      実際に付いているリソースを ENI から引き直すこと）
- [ ] NAT ゲートウェイ、VPC エンドポイントの有無
- [ ] Route 53 のホストゾーンとレコード

### C. コンピュート

- [ ] App Runner / ECS / EC2 / Lambda のうち何が使われているか、それぞれの役割
- [ ] 各サービスがどのコンテナイメージ・ランタイムで動いているか

### D. データストア

- [ ] RDS / Aurora のインスタンスとエンジンバージョン、マルチ AZ か
- [ ] ElastiCache（Redis）の構成
- [ ] S3 バケットの一覧と用途。パブリックアクセス設定がどうなっているか（設定の事実として記録する）
- [ ] バックアップの設定と保持期間
      — 何が守られているか＝何が現役とみなされているかの手がかりになる

### E. 配信

- [ ] CloudFront ディストリビューションとオリジン（どれが何を向いているか）
- [ ] ロードバランサー（ALB / NLB）のリスナーとターゲットグループ
- [ ] ACM の証明書とドメイン、有効期限
      — どのドメインがどのリソースに紐づいているかを逆算する材料

### F. 非同期処理

- [ ] SQS キューの一覧と用途、DLQ の有無と滞留の状況
      （属性で確認する。`receive-message` は本番に影響するため禁止）
- [ ] EventBridge のルールとターゲット
- [ ] Step Functions の有無

### G. 監視とログ

- [ ] CloudWatch アラームの一覧と、通知先（SNS トピックの購読先）
- [ ] ロググループの一覧と保持期間
      — 削除済みリソースの痕跡が残るため、構成の履歴を読む材料になる

### H. 権限と鍵

- [ ] IAM ロールの一覧と、それぞれの信頼関係（誰が使えるか＝何がどこに繋がっているか）
- [ ] KMS キーの一覧と用途（アプリが署名や暗号化に使っているキーがどれか）
- [ ] Secrets Manager / パラメータストアに何が置かれているか（キー名のみ。値は読めません）
      — キー名から、どのサービスが何に依存しているかが分かる

### I. 稼働状況

- [ ] 課金の内訳から、実際に動いているものを逆算する
      （「存在するか」ではなく「動いているか」を知る、ほぼ唯一の手段）
- [ ] 動いていないように見えるもの（未アタッチの EIP、空の NAT、停止中インスタンスの EBS、
      ロードバランサーに繋がっていないターゲットグループなど）。
      不要と判断せず、そう見える根拠（最終更新日時・紐づけの有無・メトリクス）を添えて記録する

---

## 成果物の書き方

共通のこと（`01_進め方.md`「成果物の置き場所」に詳しく書いてあります）。

- 生データはそのフェーズの `raw/` に落とす（`> out/<フェーズ>/raw/raw-〜.json`）
- 推測と事実を必ず区別する。「〜と思われる」「未確認」を明示すること
- 読めなかったもの（権限で拒否されたもの）も「読めなかった」と記録する
- 人が調べないと答えが出ないことは `report/ユーザー確認事項.md` に分ける
  （そのファイルだけで意図が通じるように書く）

各回の調査ログ（`log/` の中）。

- 1 回のセッション、または 1 領域につき 1 ファイル。`01_` から調べた順に増やす
- 冒頭に調査日時、末尾に使ったコマンドを書く（再現できるように）
- ここには経緯を書いてよい。前回の記述を訂正したなら、訂正したと書く

統合版（`report/構成報告.md`）。

- 調査項目の順に並べる。**調べた順・回の順に並べない**
- 現在形で、いま何がどうなっているかだけを書く。
  **経緯・訂正の履歴・「第 N 回」への言及・調査ログへの参照を書かない**
- 訂正は本文を直接書き直す。注記を足して両論併記にしない
- 根拠は `raw/` のファイル名だけ添える。`raw/` に無いものは出典を書かずに言い切る

「評価や提案を書かない」は、基礎調査というタスクの規則です。普遍の掟ではありません。
採否は `00_目的と規則.md` で決まります（上記のたたき台・`02_フェーズとは.md`）。
