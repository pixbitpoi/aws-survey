# フェーズ — いま何をするタスクなのか

この作業環境で行うことは、時期によって目的そのものが変わります。
「何があるかを調べる」のと「セキュリティを監査する」のと「構成変更の計画を立てる」のでは、
求められる成果物も、やってよいことも違います。

そこで、目的の違うひとまとまりの仕事を フェーズと呼び、1 つずつ進めます。

いま自分がどのフェーズにいるかは `out/00_進捗.md` の冒頭が正です。
そして、そのフェーズで何をするかは `00_目的と規則.md` に書かれています。
開始時に必ず両方を確認してください。

## 最重要: フェーズが変われば、守るべき規則も変わる

これを取り違えると、成果物が丸ごと目的外れになります。

たとえば フェーズ 1（基礎調査）には「評価や提案を書かない」という規則があります。
これは基礎調査というタスクの性質から来る規則で、普遍的な禁止事項ではありません。
仮にセキュリティ監査のフェーズに入れば、評価することこそが成果物になります。

| 置き場 | 内容 | 変わるか |
| --- | --- | --- |
| `AGENTS.md` / `method/` | 環境の制約と、調査の作法 | どのフェーズでも変わらない |
| `out/01_システム概要.md` | 対象システムについて分かったこと | 積み上がっていく |
| `out/<フェーズ>/00_目的と規則.md` | 目的・成果物・そのフェーズ固有の規則 | フェーズごとに変わる |

**`method/` に書かれていない「べき / べからず」を、
前のフェーズの `00_目的と規則.md` から引きずってこないでください。**
迷ったら、現在のフェーズの `00_目的と規則.md` に書いてあるかどうかで判断します。

## フェーズの目的と規則

各フェーズには `out/<フェーズ>/00_目的と規則.md` があります。 そこには必ず次の 5 つが書かれています。

| 項目 | 内容 |
| --- | --- |
| 目的 | 何のためのタスクか。何を明らかにする / 何を作るのか |
| 成果物 | 出すもの。形式（一覧・図・計画書・提案書など） |
| このフェーズの規則 | やること / やらないこと。前のフェーズとは違う場合がある |
| 入力 | 前のフェーズの成果のうち、何を土台にするか |
| 完了条件 | 何が揃えば終わりか |

これが無いフェーズは始まりません。ただし、**無いときに待つのではありません。**
**草案を書くのはあなたの仕事です。** 次に何が必要かを一番よく知っているのは、
いまこの環境で調査をしているあなただからです。

| 場面 | やること |
| --- | --- |
| `out/` に何も無い初回 | ユーザーに「このフェーズで何を明らかにしたいか」を聞き、`out/01_基礎調査/00_目的と規則.md` に草案を書く |
| いまのフェーズが終わったとき | 次に何をすべきかの案を添えて報告し、頼まれたら次のフェーズの草案を書く。使える経路（`ec2`・`code/`）をまだ使っていなければ、その案に必ず入れる |
| ユーザーが、いまのフェーズの範囲外のことを求めたとき | 選択肢を並べて決断を委ねない。次のフェーズの草案（またはいまの `00_目的と規則.md` の改訂案）をその場で書き、「承認すれば始めます」と返す（下記） |
| 進行中に不在に気づいたとき | 調査を止めて、不在を報告する |

草案は `out/<フェーズ>/00_目的と規則.md` に書き、ユーザーに読んでもらってください。

初回に聞くのは**目的だけ**です。**対象がどんなシステムかは、この時点ではまだ聞かないでください。**
基礎調査は白紙で棚卸ししてから聞く順序になっており、先に聞くと発見ではなく確認になります
（`04_基礎調査の型.md` の工程 1・2）。

採否と中身を決めるのはユーザーです。草案はたたき台であって、自分で自分の規則を決めるものではありません。
ユーザーが承認するまで、そのフェーズの調査を始めないでください。
そして、一度承認された `00_目的と規則.md` を、あとから自分で書き換えないでください。
直す必要が出たら、ユーザーに言って直してもらいます。

### 範囲外を求められたら、その返答の中で進め方を示す

ユーザーが「EC2 の中を見たい」「Lambda のコードを読みたい」「ec2 と lambda の調査を進めて」のように、いまのフェーズの
範囲外のことを求めたときは、**その 1 回の返答の中で**次のフェーズ（またはいまのフェーズの範囲の改訂）を提案し、
「はい」の一言で始められるようにしてください。「規則とのずれを解消してから」「草案を書いて承認をいただきます」のように、
これから何をするかを予告して返答を終えないでください。ユーザーは仕組みを知らず、何を待たれているのか分かりません
（`method/01` の「ユーザーには、仕組みではなく中身で話す」）。

返答に入れるのは次の 4 つで、この順です。仕組みの言葉（フェーズ・草案・承認・規則）は使いません。

1. 「分かりました。EC2 の中と Lambda のコードを調べます」と、やることを最初に言う。
2. 進め方を短く示す: 何を、どの順で、どこまで（`00_目的と規則.md` に書く目的・範囲・成果物・完了条件を、ユーザーの言葉で）。
   いまの作業で残っていること（前回の報告の見直しなど）があれば、先にやるか後にやるかも 1 行で。
3. ユーザーにしてほしいことがあれば、その場で添える: コードが無ければ `method/07` の依頼文、ホストが無ければ `method/06` の依頼文。
4. 「これでよければ『はい』と返してください。直したいところがあれば、そのまま言ってください」で締める。

ユーザーが「はい」と返したら、それが承認です。そのとき初めて `out/<NN_フェーズ名>/00_目的と規則.md` に返答と同じ内容を書き、
「フェーズを進めるときの決まり」の順で器を作って始めます。返答の前に書いてもよいですが、ユーザーに読ませるのは返答の本文です。

## フェーズ 1: 基礎調査（`out/01_基礎調査/`）

このアカウントに何があり、どう繋がっているかを明らかにする。すべての土台になるフェーズです。

- 目的・規則・完了条件は `out/01_基礎調査/00_目的と規則.md`、調査項目は `out/01_基礎調査/01_調査項目.md`
- どちらもまだ無いなら、`04_基礎調査の型.md` をたたき台にしてユーザーと作ってください
  （**この 2 つの草案が、最初のセッションの最初の仕事です**）
- 成果物も同じフォルダ
- このフェーズには「評価や提案を書かない」という規則があります。 `00_目的と規則.md` を必ず読んでください

基礎調査の中には、いくつもの段取りがあります（白紙の棚卸し → 世代の分類 → 領域ごとの深掘り →
統合 → 未解決の潰し込み → 経路の追跡）。これらはフェーズではなく、フェーズ 1 の中の工程です。
`out/01_基礎調査/` の中に「第 N 回」として積み上がっています。

## フェーズ 2 以降

何をやるかは、そのときユーザーが決めます。 あらかじめ決まった順番はありません。

基礎調査が土台になるため、多くの場合その成果（`out/01_基礎調査/`）が入力になります。
たとえば次のようなものが考えられます。これは候補の例であって、予定ではありません。

| 例 | 目的 | 基礎調査との違い |
| --- | --- | --- |
| セキュリティ監査 | リスクを見つけ、評価し、優先順位を付ける | 評価することが成果物。基礎調査の「評価しない」規則は当てはまらない |
| コスト最適化の提案 | 課金の内訳を分析し、削減案を出す | 提案することが成果物 |
| 構成変更の計画 | 特定の変更を、影響範囲と手順に落とす | 現状把握ではなくこれからの設計 |
| 新規構築の設計 | 追加するインフラを設計する | 既存を読むだけでは足りない |
| 構成図・ドキュメント作成 | 人が読むための資料を作る | 調べるのではなく伝えるための編集 |
| 定点観測 | 前回との差分を取る | 基礎調査のやり直しと比較 |

上の表を「次にやること」と読まないでください。 どれをやるか、そもそもやるかは決まっていません。
`00_目的と規則.md` が用意されて初めて、そのフェーズが始まります。

## フェーズを進めるときの決まり

フェーズを進めてよいかを決めるのはユーザーです。
現在のフェーズの完了条件を満たしたと思ったら、まず統合版の検証を通してください
（`method/05_報告の検証.md`。書いた回とは別のセッションで行います）。
そのうえで、満たした根拠と検証記録を添えて報告し、確認を取ってください。
自分の判断で次のフェーズのフォルダを作り始めないこと。

新しいフェーズを始めるときは、次の順で準備します。

1. `out/<NN_フェーズ名>/00_目的と規則.md` を確認する（無ければ、草案を書いてユーザーに承認してもらう）
2. `out/NN_フェーズ名/` と、必要なら `out/NN_フェーズ名/raw/` を作る
3. `out/00_進捗.md`（全体台帳）の「現在のフェーズ」と「フェーズの一覧」を書き換える
4. `out/NN_フェーズ名/02_進捗.md`（フェーズ台帳）を新しく作り、
   このフェーズの規則・土台にする成果物・作業リストを書く

全体台帳は薄いままにしてください。 前のフェーズの作業記録を持ち込まないこと
（`01_進め方.md`「台帳の使い分け」）。引き継ぐのは、フェーズが変わっても価値が残るものだけです。

### 前のフェーズの成果物は書き換えない

過去のフェーズのファイルは、原則そのまま残します。「いつ何が分かっていたか」が失われるためです。

- 訂正の本文は、現在のフェーズのファイルに書く
- 前のフェーズの該当箇所には、1 行だけ「→ `NN_…` で訂正」と足す

例外は `out/00_進捗.md` です。これはフェーズをまたぐ台帳なので、常に最新へ更新します。

### 前のフェーズの成果物は、読むためにある

書き換えないことと、使わないことは別です。
`out/01_基礎調査/` の調査結果と `raw/` の生データは、後続のどのフェーズでも土台として読んでください。
同じことを AWS に問い合わせ直さないこと（`01_進め方.md`「大きな出力の扱い」）。
