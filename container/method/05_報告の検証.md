# 報告の検証

統合版（`report/構成報告.md`）が、実際に取得したデータどおりに書けているかを確かめる作業です。
**書いた回とは別のセッションで行います。**

自分が書いた直後は、書いたときの記憶が残っています。「これは調べた」と思って読み進めてしまい、
文だけがあってデータが無い箇所を素通りします。間を空けて、`out/` に残っているものだけを見れば気づきます。

## いつやるか

統合版に一通り書き終えたら、その回はそこで終わりにします。次のセッションの最初の仕事がこれです。

フェーズの完了をユーザーに報告する前に、必ず 1 度は通してください（`method/02_フェーズとは.md`）。
検証していない統合版を「完成しました」と出さないこと。

## 何を見るか

統合版の記述には、根拠として `raw/` のファイル名が添えてあります
（`method/01_進め方.md`「根拠は `raw/` のファイル名だけ」）。これを使います。

| 見ること | やり方 |
| --- | --- |
| 出典のファイルが実在するか | 統合版から `raw-*.json` を拾い、そのフェーズの `raw/` にあるか確かめる。過去フェーズの `raw/` を指しているならそのフォルダを見る |
| 数と名前が合っているか | 出典付きの記述をいくつか選び、その JSON を `jq` で引いて突き合わせる。全部は見なくてよい。**どれを見るかは、選んでから JSON を開くこと** |
| 出典の無い記述に裏付けがあるか | `raw/` に無いこと（ユーザーから聞いた背景、複数の API を突き合わせて言えること）は出典を書かない決まりです。`out/01_システム概要.md` と `out/00_進捗.md` に対応する記録があるか見る |
| 調べられなかったことが書いてあるか | 拒否された操作や、権限が足りずに見られなかったものが、統合版か `ユーザー確認事項.md` に残っているか。黙って埋めていないか |
| 推測が事実として書かれていないか | 名前から用途を決めつけている箇所を探す。`raw/` のどこにも無い断定は推測です |

## 食い違いが見つかったら

**その場で書き直して終わりにしないこと。** 何がどう違ったかを残します。

1. `out/<フェーズ>/report/検証記録.md` に、見た項目・食い違い・対処を書く
2. 直せるものは統合版を直す。直したことは検証記録に書く（統合版の本文には履歴を書きません）
3. **もう一度 AWS に聞けば決まることは、聞いて決める。** これができるのがこの環境の利点です。
   引き直した生データは `raw/` に保存し、統合版の出典を新しいものに差し替える
4. 聞いても決まらないこと（ユーザーしか知らない前提）は `ユーザー確認事項.md` へ移す

出典の無い断定が `out/` のどこからも裏付けられないときは、その記述を消すか、
推測と分かる書き方に直してください。消したことも検証記録に書きます。

## 検証記録に書くこと

```
## 検証日時
## 見た範囲（出典 N 件中 M 件を突き合わせ、など）
## 食い違い（無ければ「無し」）
## 直したもの
## 引き直した問い合わせ（あれば）
## 残った未確認（ユーザー確認事項へ移したもの）
```

「全部見た」と書かないこと。**何件見たかを書きます。** 見ていないものを見たことにすると、
次の回がそこを二度と見ません。

## 終わったら

フェーズの台帳（`out/<フェーズ>/02_進捗.md`）に、検証を通したことと検証記録の場所を書きます。
これが書かれていない統合版は、まだ検証されていない統合版です。
