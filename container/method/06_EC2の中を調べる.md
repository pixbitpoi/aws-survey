# EC2 の中を調べる

AWS の API からは、インスタンスの外側（種類・タグ・セキュリティグループ・メトリクス）しか見えません。
OS の中（ログ・サービスの状態・プロセス・ディスク）は、登録済みのホストに限り `ec2` で調べられます。

```
ec2 --list                  この環境で調べられるホスト
ec2 <host> help             そのホストで使える動詞と引数の一覧
ec2 <host> <動詞> [引数...]  1 つの動詞を送り、結果を受け取る
```

登録済みのホストは `survey-status` にも出ます。何も出なければ、この対象には EC2 の中を調べる経路がありません。
ホストを足すことは、この環境ではできません。ユーザーに依頼してください。

この経路は**ログ本文を読むためのもの**です。AWS の API では塞がれているログ本文が、ここでは読めます。
読んだ内容を `out/` に写すときは、秘密らしき値（パスワード・トークン・鍵・接続文字列）を残さないでください。
ゲートウェイ側でも `***` に置き換えますが、経験則であり、すべては拾えません。

## 何ができて、何ができないか

EC2 側には診断ゲートウェイがあり、決められた動詞だけを、シェルを経由せずに実行します。
動詞は `ec2 <host> help` が正です。大きく 3 つに分かれます。

| 段 | 動詞 | 何が読めるか |
| --- | --- | --- |
| 一般読み取り | `ls` `find` `stat` `du` `cat` `head` `tail` `grep` | ログインユーザーの権限で読める任意のパス。絶対パスのみ |
| 固定診断 | `uptime` `os` `ps` `proc` `free` `vmstat` `df` `sar` `net` `services` `failed` `service` `unit` `timers` `journal` `logs` | OS とサービスの状態。引数は決まった形だけ |
| root 読み取り | `listeners` `dmesg` `cron` `journal` `log` | root でないと読めないもの。**登録済みログと固定の診断だけ** |

この環境ではできないこと。回避しないでください。

- `ssh` / `scp` / `sftp` を直接使うことはできません。入口は `ec2` だけです
- シェル・任意のコマンド・`sudo` は実行できません。動詞に無いものは `denied:` で返ります
- 書き込み・削除・再起動・プロセスの停止はできません
- `tail -f` のような追尾、`top`、`strace`、`tcpdump`、`curl` はありません
- 秘密らしき名前のファイル（`.env`、`*.pem`、`*.key`、`id_*`、`*secret*`、`*credential*`、`*password*`、`wp-config.php`、
  `database.yml` など）と、秘密の置き場（`/root`、`~/.ssh`、`~/.aws`、`/etc/ssh`、`/etc/shadow`、`.git/`、`/proc/*/environ`）は
  読めません。`ls` の一覧には名前が出ますが、`cat` / `tail` / `grep` の対象にはなりません
- データベースの本体（`*.sqlite`、`*.db`）は読めません
- OS の権限で読めないものは、上の一覧に無くても読めません（`stat` で権限は見えます）
- 感度の高いホストは一般読み取り段が無効になっていることがあります（`strict mode` の理由で拒否されます）。
  そのホストでは固定診断と root 読み取り段だけを使ってください
- `ec2` は単独で実行します。パイプ・`;`・`&&`・`$()` との組み合わせは実行できません。
  保存は `> out/<フェーズ>/raw/名前.txt` の形だけ通ります
- 出力は 1 MiB で打ち切られ（末尾に `[truncated]`）、1 つの動詞には時間の上限があります。同時に送れるのは 1 本です

実行した要求は、通った・拒否されたにかかわらず EC2 側にも記録が残ります。

## 進め方: 場所を突き止めてから、読む

ログの場所は事前に分かりません。**一覧と検索で当たりを付けてから、本文を読む**のが基本です。
いきなり `cat` しないでください。大きなファイルを文脈に流し込むと、セッション時間を使い切ります。

1. **何が動いているか**: `services`、`failed`、`ps --top 30`、`listeners`。
   どこと繋がっているかは `net`（確立済みの TCP 接続。プロセス名は出ません。短時間だけ張る接続は、たまたま張られていたときにしか見えません）
2. **どこに書いているか**: `ls /var/log`、`find /var/log --name '*.log' --newer 2026-09-01`、`unit <unit>`（設定ファイルのパスが分かる）、
   `du /var/log --depth 1`（どれが大きいか）
3. **どれくらいあるか**: `stat <path>`（サイズ・更新時刻）。`logs`（root でないと読めない登録済みログの一覧と実ファイル）
4. **末尾から読む**: `tail <path> --lines 200`。ローテート済みの `.gz` もそのまま読めます
5. **絞る**: `grep <path> --pattern 'ERROR|Timeout' --context 2 --max 200`。複数のパスを並べられます
6. **時系列で見る**: `journal <unit> --since 2h --priority err`、`dmesg --lines 200`

登録済みログ（`logs` に出るもの）は `log <名前> --tail N --grep <pat>` で読みます。
`tail` / `grep` で `Permission denied` になるファイルが `logs` にあれば、そちらが正しい入口です。
`logs` に無く、権限でも読めないものは「読めなかった」と記録してください（`01_進め方.md` 大原則 3）。
`journal` はグループで読めなければ自動で root 読み取り段に回るので、使い分けを意識する必要はありません。

## 大きな出力は `raw/` に落とす

`aws` と同じ作法です。数百行を超えそうな動詞は、まずファイルに保存してから、必要な部分だけ読んでください。

```
ec2 web1 services > out/<フェーズ>/raw/raw-web1-services.txt
ec2 web1 tail /var/log/nginx/error.log --lines 2000 > out/<フェーズ>/raw/raw-web1-nginx-error.txt
grep -c 'upstream timed out' out/<フェーズ>/raw/raw-web1-nginx-error.txt
```

| 決まり | 内容 |
| --- | --- |
| 保存先 | 現在のフェーズの `raw/`。拡張子は `txt`（`ec2` の出力はテキスト） |
| 命名 | `raw-<host>-<何>.txt`。ホストが複数あるので、名前にホストを入れる |
| 読み方 | 保存したファイルには `grep` / `sed` / `head` を普通に使える。制約があるのは `ec2` を含む行だけ |
| 再利用 | 同じ範囲を取り直さない。ログはその場で伸びるので、取り直すと突き合わせが崩れる |
| 記録 | その回の調査ログの末尾に、打った `ec2` コマンドを列挙する（`01_進め方.md` 大原則 4） |

`raw/` に保存したログ本文は `out/` の他のファイルと同じ扱いです。統合版に写すときは、必要な行だけを引用し、
秘密らしき値と個人が特定できる情報（IP・ユーザー名・メールアドレス）は、ユーザーと決めた扱いに従ってマスクしてください。

## 拒否と失敗の読み方

| 返り方 | 意味 | どうするか |
| --- | --- | --- |
| `denied: ...`（終了コード 2） | 動詞・引数・パスがゲートウェイの決まりに合わない | 理由を読んで書き方を直す。決まりの外にあるものは諦めて記録する |
| `Permission denied` | OS の権限で読めない | `logs` にあれば `log` で。無ければ「読めなかった」と記録 |
| `strict mode` | このホストは固定診断と root 読み取り段だけ | 一般読み取り段の動詞を使わない |
| 終了コード 255（接続に失敗） | 資格情報の期限切れか、接続の不調 | `survey-status` を見る。期限切れなら保存と台帳の更新を先に |
| `ec2: 接続が異常終了したため…` | 接続の後片付けをした報せ | 何もしなくてよい。同じ動詞を打ち直してよい |
| `ec2: 前回までの接続で残っていた…` | 前回までの接続が残したものを、今回の接続の前に片付けた報せ | 何もしなくてよい。結果はそのまま使える |

拒否は異常ではありません。塞いであるものを回避しようとせず、`denied:` の内容と一緒に記録してください。

## いつ使うか

そのフェーズの `00_目的と規則.md` が OS の中を見ることを求めているときだけです。
基礎調査（`04_基礎調査の型.md`）は AWS の API で外側を棚卸しする工程で、EC2 の中は次のフェーズの材料になることが多い。
中を見ることで初めて答えが出る問い（「このインスタンスで何が動いているか」「エラーの原因は何か」）を、
フェーズの目的にしてから使ってください。
