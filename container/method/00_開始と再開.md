# 開始と再開

- `survey-status` … 資格情報の残り時間と、いま何をすべきか。現在のフェーズ名も出る
- `ls out/` … これまでに何が積み上がっているか

フェーズ名は `out/` の中のフォルダ名（`_環境/` を除く）。
正は `out/00_進捗.md` の冒頭だが、それがまだ無いときは `ls out/` で分かる。

## `out/` に何も無いなら、そこから作る

`out/` が空、または下記が欠けているなら初回。順に埋める。飛ばさないこと。

| 順 | 無ければ、やること |
| --- | --- |
| 1 | `out/_環境/00_動作確認.md` が無い、または使用エージェントの確認が未実施 → `method/03_環境の確認.md` に従い、この環境で何ができるかを確かめる。まずこれ |
| 2 | `out/00_進捗.md` が無い → 全体の台帳を作る（`method/01_進め方.md`） |
| 3 | `out/01_システム概要.md` が無い → 見出しだけ作る。中身はまだ書かない |
| 4 | `out/<フェーズ>/00_目的と規則.md` が無い → ユーザーに聞いて草案を書き、承認をもらう（下記・`method/02_フェーズとは.md`） |
| 5 | `out/<フェーズ>/01_調査項目.md` が無い → 何を調べるかの一覧を作る。基礎調査なら `method/04_基礎調査の型.md` がたたき台 |
| 6 | `out/<フェーズ>/02_進捗.md` が無い → フェーズの台帳を作る |

**最初のフェーズは基礎調査。** 器のフォルダは既にあることが多い（`ls out/` で分かる）。
無ければ `out/01_基礎調査/` として自分で作る。これは他のフェーズの土台になるので、先に別のことをしない。
ユーザーが別のことから始めたいと言うなら、その名前で作る。

`00_目的と規則.md` をユーザーが承認するまで調査を始めない。
何をするフェーズか決まっていないまま調べると、成果物が目的外れになる。

### 草案のために聞くのは、目的だけ

聞くのは「**このフェーズで何を明らかにしたいか**」だけ。
**対象がどんなシステムかは、ここではまだ聞かない。**

`out/01_システム概要.md` の中身も、この段階では埋めない。
最初のフェーズが基礎調査なら、先に白紙で棚卸しする（`method/04_基礎調査の型.md`）。
何があるはずかを先に聞くと、発見ではなく確認をすることになり、想定外のものを見落とす。

ユーザーが自分から話し始めたら、止めなくてよい。聞いたことは `out/01_システム概要.md` に書く。
こちらから水を向けないというだけ。

## 揃っていれば、この順で読む

| 順 | 読むもの | 何が分かるか |
| --- | --- | --- |
| 1 | `out/00_進捗.md` | いまどのフェーズか。全体の状況 |
| 2 | `out/<現在のフェーズ>/00_目的と規則.md` | 今回の目的・成果物・このフェーズの規則・完了条件 |
| 3 | `out/<現在のフェーズ>/02_進捗.md` | そのフェーズの現在地と、次にやること。統合版が検証済みかもここで分かる |
| 4 | `out/01_システム概要.md` | 対象システムについて、これまでに分かっていること |
| 5 | `out/02_調査ノウハウ.md` | 前の回が見つけた、次も効く調べ方と読み違いの類型 |
| 6 | `method/` | 調査の作法とフェーズの考え方（初回とセッション再開時） |

統合版（`report/構成報告.md`）があるのに、フェーズの台帳に検証を通した記録が無いなら、
**このセッションの最初の仕事は調査ではなく検証です**（`method/05_報告の検証.md`）。
書いた回とは別の回が見ることに意味があるので、先に新しい調査を始めないでください。

ここで行う仕事は、時期によって目的そのものが変わる。
「何があるかを調べる」ときもあれば、「セキュリティを監査する」「構成変更の計画を立てる」
「図やドキュメントを作る」ときもある。目的の違うひとまとまりの仕事をフェーズと呼ぶ。

前のフェーズの規則を今のフェーズに持ち込まないこと。
基礎調査の「評価や提案を書かない」は基礎調査というタスクの規則であって、
普遍的な禁止事項ではない。今回の「やること / やらないこと」は今回の `00_目的と規則.md` だけが決める。
