# 開始と再開

- `survey-status` … 資格情報の残り時間と、いま何をすべきか。登録済みの EC2 ホストと取り出してある Lambda のコードも出る
- `ls -A out/ out/.survey/ out/report/` … これまでに何が積み上がっているか（`.survey/` はドットで始まるので `-A` が要る）

`out/` だけが記憶です。会話の中に置いたことは、セッションが終わった時点で消えます。

## `out/` に何も無いなら、基礎調査から

`out/` が空、または `out/report/構成報告.md` がまだ無いなら、基礎調査の途中です。順に埋めます。

| 順 | 無ければ、やること |
| --- | --- |
| 1 | `out/.survey/env/check.md` が無い、または使用エージェントの確認が未実施 → `method/03_環境の確認.md`。まずこれ |
| 2 | `out/.survey/state.md` が無い → 台帳を作る（`method/01_進め方.md`「台帳」） |
| 3 | `out/report/前提.md` が無い → 見出しだけ作る。中身はユーザーから聞いたときに書く |
| 4 | `out/report/構成報告.md` が無い → `method/04_基礎調査の型.md` に従い、生データを集めて報告まで書く |

基礎調査は他のすべての土台なので、先に別のことをしません。**ユーザーに目的を聞いてから始めるものではありません。**
何があるかを白紙で調べ、報告を書き、それを手にユーザーと話すのが順序です。
何があるはずかを先に聞くと、発見ではなく確認になり、想定外のものを見落とします。

途中で終わった回があれば（`raw/` はあるが `report/` が無い、`state.md` に途中と書いてある）、続きからです。
`raw/` にある生データを読み、同じ問いに API を叩き直さないでください。

## ユーザーが応答できない回

最初の指示に「この回はユーザーが応答できない」とあれば、聞く工程を飛ばし、聞かずにできることをすべてやって終えます。
報告がまだ無い回と、報告があってから経路（EC2 の中・Lambda のコード）が足された回の両方が、この形で来ます。

| 順 | やること |
| --- | --- |
| 1 | 上の表の 1（`method/03_環境の確認.md`）。期待と違うものがあれば `out/.survey/env/check.md` の冒頭に大きく書き、それ以上進めずに終える |
| 2 | 上の表の 2〜3（台帳と前提の見出し） |
| 3 | `report/構成報告.md` が無ければ、`method/04_基礎調査の型.md` を最後まで。生データを `raw/` に集め、報告と `report/ユーザー確認事項.md` を書き切る。あれば、まず `method/05_報告の検証.md` で検証する |
| 4 | `survey-status` に出ている経路があれば、聞かずに読む。登録済みホストは `ec2 <host> …`（`method/06`）、取り出してあるコードは `code/`（`method/07`）。分かったことを報告の本文（系統の節）に書き直し、`ユーザー確認事項.md` の「中を見れば分かること」から該当を消す |
| 5 | `ユーザー確認事項.md` の回答欄に書かれていれば、`report/前提.md` に移して報告を書き直し、その問いを消す |
| 6 | `state.md` に現在地を書く。報告まで書けたなら「基礎調査の報告済み。次はユーザーと話す」、途中なら「どこまで終わり、何が残っているか」 |

この回は、時間で切り上げないでください。**この回のあいだ、一時キーは自動で入れ替わります。**
`survey-status` の残り時間が減っても、次に見たときには増えています。長い作業の前に見直す必要はありません。
`ExpiredToken` が実際に出たときだけ、書きかけを保存して台帳を更新し、終えてください（`method/01`「`ExpiredToken` が出たら」）。

やらないこと: ユーザーに聞く（聞きたいことは `report/ユーザー確認事項.md` に書く）、評価や提案を書く（`method/04`）。
経路の無い EC2 やコードを取り出していない Lambda は、中を見る価値があるものを確認事項に依頼文つきで挙げます。

Cost Explorer が読めなくても、有効化の依頼は確認事項に書き、代わりの入口で続けます（`method/01` の「効率のよい入口」）。

## 揃っていれば、この順で読む

| 順 | 読むもの | 何が分かるか |
| --- | --- | --- |
| 1 | `out/.survey/state.md` | いま何の作業をしているか、現在地、次にやること、決定事項。報告が検証済みかもここで分かる |
| 2 | `out/report/ユーザー確認事項.md` | ユーザーに聞いていること。**回答欄に書かれていれば、それが最初の入力** |
| 3 | `out/report/構成報告.md` | 人に渡した報告 |
| 4 | `out/report/前提.md` | 対象について、ユーザーから聞いて分かっていること |
| 5 | `out/.survey/notes.md` | 前の回が見つけた、次も効く調べ方と読み違いの類型 |
| 6 | `method/` | 調査の作法（初回とセッション再開時。`01` は必ず、あとは必要なものを） |

報告（`report/構成報告.md`）があるのに、台帳に検証を通した記録が無いなら、
**このセッションの最初の仕事は検証です**（`method/05_報告の検証.md`）。書いた回とは別の回が見ることに意味があります。
ただし、ユーザーが先に何かを聞いてきたら、そちらに答えてからで構いません。検証は数分で済む作業です。

## 対話の回で、何から始めるか

ユーザーの言うことに従います。指示が来たらそれをやり、質問が来たらそれに答えます。
台帳の「次にやること」は、ユーザーが何も言わないときの既定であって、ユーザーの求めより優先しません。

「調査を進めて」のように何をするかが決まっていないときは、`report/ユーザー確認事項.md` を手に、次を提案します。

1. 「中を見れば分かること」に挙げたもののうち、`survey-status` に出ている経路（登録済みホスト・取り出してあるコード）で
   いま読めるものがあれば、聞かずに読んで報告を埋める（`method/06` / `method/07`）
2. まだ経路が無いものは、用意してもらう依頼文（`method/06` / `method/07`）をそのまま伝える
3. 「ユーザーにしか分からないこと」を、答えやすい順に聞く

答えを `report/前提.md` に、分かったことを `report/構成報告.md` の本文に反映します（`method/02_基礎調査のあと.md`）。
