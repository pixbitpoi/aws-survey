# aws-survey - エージェントのためのAWS調査ツール

AWSのインフラ構成をコーディングエージェントに「安全に」調査させる cli ツールです。

```bash
$ brew install aws-survey
$ aws-survey
...あとはガイダンスにしたがうだけ...
```

構成が不明なインフラを、学習コストゼロで、簡単・安全・自動的に調査できます。

- 🔒 安全な操作 — 厳格なポリシーを適用した一時的なクレデンシャルにより、セキュアな調査が可能です。
- 🔑 秘匿情報の隠蔽 — S3 のオブジェクト、Secrets Manager、ログ本文など秘匿情報がありそうな経路をエージェントに隠します。
- 👷 監査可能 — 実行された AWS コマンドは全て記録されます。別のエージェントに実施内容を監査させることも可能です。
- 💰 効率的 — 調査結果を再利用可能な形で蓄積するため、トークン効率にすぐれています。また、複数回のセッションに分けて調査できます。

難しい設定はありません。空のフォルダをつくって `aws-survey` と打てば対話的に進行します。

## 事前準備 - 安全な調査コンテナの作成

### 1. 必要なツールの準備

- AWS CLI と Docker を事前に導入してください。
- Docker Desktop は Settings → Resources → File Sharing に登録した場所しかマウントできません。Homebrew で入れた本体は
  `/opt/homebrew` の下にあるので、`/opt/homebrew` を追加して Apply & restart してください（`aws-survey doctor` と `aws-survey run` が
  足りない場所を案内します）。
- AWS CLI で調査対象にアクセスできる状態にしてください。
- 元プロファイルのログインには [aws-login](https://github.com/pixbitpoi/aws-login) を使います。
  brew の依存に入っているので、`aws-survey` と一緒に入ります。
- macos を前提としています。

### 2. インストール

```bash
$ brew tap pixbitpoi/tap
$ brew trust pixbitpoi/tap
$ brew install aws-survey
```

### 3. 調査環境のセットアップ

1. 調べたい AWS アカウントごとに空のフォルダを作成してください。以降、そこが作業スペースとなります。

   ```bash
   $ mkdir -p ~/surveys/example
   $ cd ~/surveys/example
   ```

2. aws-survey コマンドの実行

   ```bash
   $ aws-survey
   ```

   初回実行時は AWS への接続方式について、ひとつずつ確認されます。  
   以降は「次はこれを実行しますか？ (Y/n)」と聞かれるので、Enter を押していくだけで、
   ロールの作成・一時キーの発行・読み取り専用の検証を経て、調査コンテナの起動まで進みます。  
   途中で `n` と答えれば、そこで止まって次に打つコマンドが表示されます。改めて `aws-survey` を打てば続きから再開します。

3. セットアップの完了

   セットアップ完了後のフォルダ構成は、以下のとおりです。  
   
   ```
   ~/surveys/example/  
     ├── environment.json  ...   AWS への接続情報  
     ├── trust.json        ...   ロールの信頼ポリシー  
     ├── AGENTS.md         ...   エージェントへの指示  
     ├── CLAUDE.md  
     └── out/              ...   調査結果の格納用フォルダ  
   ```

   接続情報やエージェントへの指示事項が作成されます。  
   調査結果は out/ フォルダに作成されますが、セットアップ時点では空となっています。

## 調査の開始

### 1. 調査用コンテナとエージェントの起動

1. コンテナの起動

   セットアップの最後では `aws-survey run` の実行を聞かれます。Enter を押せばそのまま調査用のコンテナが起動します。  
   あとから起動するときは、このコマンドを直接打つか、`aws-survey` を打ち直してください。

   ```bash
   $ aws-survey run
   ```

2. エージェントの起動
   
   claude や codex を起動し、認証を行なってください。  
   多くの場合、サブスクリプションを利用した認証を行うと思いますが、認証情報は保存されるので次回以降の起動では聞かれません。

   ```bash
   $ claude
   ```

### 2. 調査

調査は自動的に進行し、ほぼオートパイロットです。  
指示をしなければ、まず基礎調査を行い、次に詳細な調査へとフェーズを区切りながら進行します。  
もっとも、対話的に進めますので、進め方は自由です。エージェントに相談してください。

1. 基礎調査の開始

   ```bash
   $ claude
   ❯ 調査を進めてください
   ```

   このように雑な指示でも大丈夫です。

2. 基礎調査の結果

   ```
   ~/surveys/example/
   └── out/
       ├── 00_進捗.md
       ├── 01_システム概要.md
       ├── 02_調査ノウハウ.md
       ├── _環境/
       │   ├── 00_動作確認.md
       │   └── aws-audit.log
       └── 01_基礎調査/
           ├── 00_目的と規則.md
           ├── 01_調査項目.md
           ├── 02_進捗.md
           ├── report/
           │   ├── 構成報告.md
           │   └── ユーザー確認事項.md
           ├── log/
           └── raw/
   ```

   調査を続けると `02_詳細調査/` のようにフェーズが増えていきます。

   特に細かい指示をしなくとも、次の9つの領域を横断して棚卸ししてくれます。  
   どんなリソースがあるのかすら不明な環境でも、利用料金などから自動的にリソースを特定していきます。

3. レポートの確認

   各フェーズごとの report フォルダにユーザー向けの報告や、エージェントからユーザーへの確認依頼などが溜まっていきます。  
   レポートの解釈なども含め、不明な点があれば、エージェントにただ聞くだけです。

### 3. EC2 の中を調べる（任意）

AWS の API から見えるのはインスタンスの外側だけです。OS の中（ログ・サービスの状態・プロセス・ディスク）まで
調べたいときは、そのインスタンスにだけ診断ゲートウェイを導入します。導入は強い権限の元プロファイルで 1 コマンド、
接続は SSM 経由（Session Manager）なので、インバウンドの穴を開けません。対象が SSM 管理下（`AmazonSSMManagedInstanceCore`）にあることが前提です。

```bash
$ aws-survey ssh setup web1        # Name タグか instance-id。ゲートウェイの導入・鍵の配布・タグ付け
$ aws-survey role --create         # 接続を許すポリシーを調査用ロールに足す（既にあるものは変わりません）
$ aws-survey credentials           # 一時キーを発行し直す
$ aws-survey ssh verify web1       # 通るもの・塞がっているものを、実際に接続して確かめる
$ aws-survey run
```

後片付けと鍵の更新もコマンドで行います。

```bash
$ aws-survey ssh remove web1       # ユーザー・ゲートウェイ・sshd と sudoers の設定を EC2 から撤去し、タグと記録を消す
                                   # 最後のホストなら、接続を許すポリシーも調査用ロールから外して消す
$ aws-survey ssh rotate            # 鍵を作り直して、登録済みホスト全部に再導入する
```

調査コンテナの中では `ec2 <host> <動詞>` で使います。エージェントは `survey-status` に出るホストを見て、
自分で `method/06_EC2の中を調べる.md` に従って進めます。

```
ec2 web1 help                                       使える動詞の一覧
ec2 web1 services                                   systemd のサービス一覧
ec2 web1 tail /var/log/nginx/error.log --lines 200  ログの末尾
ec2 web1 journal nginx --since 2h --priority err     journal の直近のエラー
```

EC2 側では決められた動詞だけがシェルを経由せずに動き、書き込み・再起動・任意のコマンドはそもそも存在しません。
root でしか読めないものは、登録済みのログと固定の診断だけです。秘密らしき名前のファイルは読めず、本文の秘密らしき値は
マスクされますが、マスクは経験則です。何が保証され、何が保証されないかは
[`security.md`](./docs/security.md) の第 4 節と第 6 節にあります。

### 4. Lambda のコードを読む（任意）

AWS の API から分かるのは関数の設定までです。関数が何をしているか（呼んでいるサービスとリソース、使っている環境変数、接続先）まで
調べたいときは、デプロイされているコードをホストで取り出して、調査コンテナに読み取り専用で渡します。

```bash
$ aws-survey lambda pull my-function     # 関数名（複数可）。そのリージョンの全関数なら --all
$ aws-survey lambda list                 # 取り出してある関数とレイヤー
$ aws-survey run
```

取り出しは、Lambda のコードを読むことだけを許した 15 分の一時キーで行い、そのキーはファイルに書きません。
展開はネットワークも資格情報も無い使い捨てのコンテナで行い、秘密らしい名前のファイルは除き、コードの中の秘密らしい値はマスクします。
依存ライブラリは既定で除き、名前と版の一覧だけを残します（`--with-deps` で含めます）。関数は起動しません。
取り出したコードは対象フォルダの `code/` に置かれ、`aws-survey lambda remove <関数名>`（全部なら `--all`）で消せます。
コードが変わっていなければ、もう一度 `pull` しても落とし直しません。

調査コンテナの中では、エージェントが `survey-status` に出る件数を見て、`method/07_Lambdaのコードを読む.md` に従って読みます。

コードは対象の資産です。取り出す前に、対象の管理者と合意しておいてください。何が保証され、何が保証されないかは
[`security.md`](./docs/security.md) の第 5 節と第 6 節にあります。

## 補足

### A. 調査対象の一例

特に細かい指示をしなくとも、次の9つの領域を横断して棚卸ししてくれます。  
どんなリソースがあるのかすら不明な環境でも、利用料金などから自動的にリソースを特定していきます。

| 領域 | 調査内容 |
| --- | --- |
| 全体像 | 実際に動いているリソース、`prod` / `stg` / `dev` の分離、世代や系統 |
| ネットワーク | VPC・サブネット、セキュリティグループが何をどこから受けているか、Route 53 |
| コンピュート | App Runner / ECS / EC2 / Lambda のどれが何の役割で動いているか |
| データストア | RDS・ElastiCache・S3（公開設定を含む）、バックアップの保持 |
| 配信 | CloudFront のオリジン、ALB / NLB のターゲット、証明書とドメインの紐づけ |
| 非同期処理 | SQS と DLQ の滞留、EventBridge のルール、Step Functions |
| 監視とログ | アラームと通知先、ロググループと保持期間 |
| 権限と鍵 | IAM ロールの信頼関係、KMS、Secrets のキー名（値は読めません） |
| 稼働状況 | 課金の内訳から「動いているもの」を逆算。未アタッチの EIP や空の NAT も |

次の2つの調査結果が出力されます。
- `構成報告.md` 詳細レポートです。
- `ユーザー確認事項.md` エージェントから人間への質問です。調査のブロック要因などが記載されます。

※ エージェントと対話して作業しますから、実際には成果物は柔軟に決められます

### B. 安全確保の仕組み

本番アカウントの AI 調査では、サービスの破壊や秘匿情報の漏洩が課題となります。

| 課題 | 対策 |
| --- | --- |
| 破壊される | 書き込み系の API は AWS 側が拒否します |
| 秘匿情報の漏洩 | S3 のオブジェクト、Secrets、ログ本文など、値を読む API を個別に塞いであります（任意機能のうち、EC2 の中を調べる機能はログ本文を、Lambda のコードを読む機能はデプロイされたコードを読みます。上記 3・4） |
| 料金がかかる | 従量課金の API は、実行前のフックが読み取り系の動詞以外を通しません |

「読み取り専用にしたから安全」ではありません。AWS 標準の `ReadOnlyAccess` は、S3 のファイル本文も、DynamoDB のレコードも、ログ本文も、`sqs:ReceiveMessage`（読み取りなのに本番のキュー処理に影響します）も許してしまいます。そこからさらに削った一時キーを発行しているのは、そのためです。

その上で、性質の違う 3 つの防御を重ねています。1 つ破られても、残りが効きます。

| 防御策 | 詳細 |
| --- | --- |
| AWS 側の判定 | 削り込んだ読み取り専用の一時キーしか渡さない。書き込みは AWS が拒否する。最後の砦 |
| コンテナの境界 | 強い権限のキーもリポジトリも、コンテナの中に存在しない。`sudo` も入れていない |
| 実行前のフック | 危険な形のコマンドを実行前に止め、検査した AWS コマンドを記録する |

報告が本当かどうかの突き合わせは自動で行われます。叩かれた AWS コマンドは全て記録され、
フェーズを完了扱いにする前に報告と突き合わされます。結果が怪しければ `out/_環境/aws-audit.log` を自分の目で見てください。

> [!IMPORTANT]
> 調査前にご一読ください。  
> [`security.md`](./docs/security.md) — 脅威モデル、セッションポリシーの設計、フックの判定順序、
> そして**この一式が保証しないもの**をまとめてあります。

### C. 開発者向けの情報

[`AGENTS.md`](AGENTS.md) に、構造と、変更するときの不変条件が書いてあります。
本体（このリポジトリ）と対象フォルダ（`environment.json` と `out/`）は別の場所です。
開発中はこのリポジトリ直下を対象フォルダにしても動きます。

開発版（`main` の最新）は `brew install --HEAD pixbitpoi/tap/aws-survey` で入ります。
リリース手順と配布物の範囲は [`docs/release.md`](docs/release.md) にあります。
